# OpenCodeReview 审查规则

请使用简体中文完成审查。代码中的类名、方法名、变量名、字段名、接口地址、枚举值、SQL 表名和配置项保持原样。

## 一、审查原则

1. 重点审查本次 MR 相对于目标分支新增或修改的代码；不要把历史遗留问题写成本次引入。
2. 每个问题必须有代码证据：文件、行号、实际执行路径、触发条件和可解释的错误结果。没有证据的推测不能作为问题报告。
3. 同一个根因影响多个位置时合并报告，列出全部受影响位置，避免重复报告。
4. 不报告纯风格偏好、主观重构建议或“未来可能有风险”但无法证明的问题。
5. 先给结论，再用简短案例说明；避免大段抽象描述。

## 二、重点检查

1. 业务逻辑：成功、失败、空数据、重复提交、异常和边界条件。
2. 权限安全：登录态、租户隔离、数据归属、横向越权；不得直接信任客户端的 `accountCode`、`userCode`、`userPhone`、`userId` 等身份字段。
3. 链路契约：Controller、DTO、VO、Service、Mapper、数据库和前端调用的字段、类型、枚举、状态和分页是否一致。
4. SQL 数据：条件、数据范围、空条件查询、分页、排序、重复列、NULL、逻辑删除、索引和敏感数据泄露。
5. 异步一致性：事务边界、MQ 发送、重试、幂等、重复消费、失败恢复和最终状态。
6. 数据库升级：字段、默认值、长度、索引、迁移脚本和旧库升级兼容性。
7. 前端行为：接口地址、HTTP 方法、请求/响应字段、错误处理、权限、空数据、重复操作和页面回显。

## 三、证据和案例要求

每个确定性问题都必须尽可能包含以下内容：

1. 触发案例：使用具体输入、数据状态、接口参数或调用顺序。例如：`invoiceStatus` 省略、`card_write_off_time IS NULL`、旧库未增加新字段、同一请求重复提交两次。
2. 执行结果：说明代码会走哪条分支、查询返回什么、哪条数据被漏掉/重复/覆盖，或哪个接口/测试会失败。
3. 影响数据：能计算时给出具体示例。例如 100 条记录中 20 条被过滤、第二页查询跳过前 50 条；不能确认数量时写明影响范围和数量取决于实际数据。
4. 影响对象：明确是页面、导出、接口调用方、数据库升级、订单状态、金额、库存还是权限安全。
5. 不要把“可能”“也许”“有风险”直接写成确定问题。若缺少运行环境、配置、调用方、数据或业务规则证据，移到“需要确认”，不要列入 Bug。

## 四、风险等级

1. `HIGH`：已由代码逻辑直接证明会造成越权、敏感数据泄露、错误扣款/提现、严重数据破坏、核心流程不可用或生产升级失败。
2. `MEDIUM`：已由代码逻辑直接证明会造成正常业务条件下的功能错误、数据漏算/多算、接口契约错误、状态错误、事务/异步不一致或明显性能问题。
3. `LOW`：缺陷事实和触发条件已经确认，但影响较小。LOW 不是收纳推测的等级。
4. 无法证明问题真实存在时，不得分配任何风险等级，也不得计入问题数量；只列入“需确认事项”。
5. 风险等级必须说明依据，不得仅因为代码改动较大或看起来不规范就提高等级。

## 五、固定输出格式（必须严格遵守）

每个已确认问题都必须完整输出以下 12 个字段，字段名称、顺序和冒号保持不变，不得省略字段。字段没有内容时必须填写“无”，不得留空、删除字段或使用英文占位符。每个问题单独编号，从 `问题 1` 开始连续编号。

```text
问题 1
标题：<一句话说明什么场景下产生什么错误结果>
风险等级：<HIGH/MEDIUM/LOW>
问题类型：<Bug/Security/Performance/其他>
问题来源：<本次引入/历史遗留>
代码位置：<文件相对路径；类/方法；准确行号>
接口信息：<HTTP 方法、接口地址、关键请求参数、响应字段；没有接口写“无”>
问题描述：<当前代码 + 触发条件 + 实际错误结果；包含可验证的具体案例>
影响分析：<影响对象 + 影响范围 + 实际后果；没有影响写“无”>
修复方案：<明确到文件、方法、条件、数据处理或配置的可执行修改>
修复后代码：<可直接落地的代码块；没有可靠代码时写“无法在当前上下文中可靠生成完整修复代码”，再给出准确修改位置和伪代码>
验证方式：<测试数据、接口请求、单测、SQL/EXPLAIN、构建或联调步骤及预期结果>
需确认事项：<修复前仍需业务确认的内容；没有写“无”>
```

补充要求：

1. `代码位置`、`接口信息`、`需确认事项` 是必填关键字段，即使没有内容也必须保留并写“无”。位置必须尽量写到文件、类/方法和行号；无法定位时写“无法从当前代码准确定位”，不能猜测。
2. `接口信息`不能用“相关接口”代替。能从 Controller、路由、前端调用或接口文档确认时，写出完整 HTTP 方法和地址；无法确认时写“无法从当前代码确认”，不要编造地址。
3. `需确认事项`只记录不影响问题成立的业务选择；如果问题本身是否成立依赖未确认前提，不能放在问题列表，必须放入后面的“需确认事项”独立栏目。
4. `修复后代码`必须优先给出修改前后关键代码。代码不完整或上下文不足时，必须明确写无法可靠生成，不得编造不存在的 API、字段、注解、表或方法。
5. `问题描述`和`影响分析`必须简洁易懂，优先用“示例数据：输入/数据状态 -> 实际结果；预期结果 -> 差异”的形式。示例数据必须标明是示例，不能冒充线上真实数据。

## 六、必须放入“需确认事项”的情况

以下情况不能直接算作 Bug：

1. 不确定某个字段、枚举或状态的业务定义。
2. 不确定调用方是否会传入某个参数，或接口是否真的被使用。
3. 不确定 MyBatis、事务、逻辑删除或其他拦截器在当前环境中的实际行为。
4. 不确定数据库版本、配置、索引、历史数据或部署升级顺序。
5. 不确定某种导出列顺序、报表口径或兼容规则是否为正式业务契约。
6. 只能提出理论上的性能风险，但没有数据规模、执行计划或调用频率证据。

“需确认事项”必须写清楚：确认什么、通过什么代码或数据确认、确认结果分别对应什么处理结论。仅有待确认事项时，不要创建 Bug 审查项，并使用以下固定格式：

```text
需确认事项
1. 确认内容：<需要确认什么>
   确认方式：<查看哪段代码、配置、数据库或调用记录>
   结论影响：<确认成立时如何处理；不成立时如何处理>
```

没有待确认内容时输出：`需确认事项：无`。

## 七、输出约束

1. 所有字段名称、问题标题、描述、影响、修复、验证和需确认事项使用简体中文；`Bug`、`Security`、`Performance`、`HIGH`、`MEDIUM`、`LOW` 等分类标签可保留英文。
2. 只报告明确的问题；没有可确认问题时写“未发现可以确认的问题”。
3. 历史问题写明“历史遗留”，无法确认首次提交时不得编造 Commit。
4. 修复建议必须与已验证事实区分；建议中的代码不能冒充已验证结果。
5. 必须使用第五节的固定字段顺序。每个字段只写与本问题直接相关的内容；已由工具展示的路径、等级和代码仍不得省略字段。非代码正文尽量控制在 200～400 个汉字，复杂链路可适当增加。
6. 案例中的虚构订单号、金额、数量必须标明“示例数据”，并且运算和结果能由当前代码推导；不能冒充线上数据或已执行测试。案例应同时写出预期结果与实际代码结果。
7. 例如：“示例数据：发票 A 金额 100 元，已禁用。历史同步仍写入这 100 元；预期报表不包含 A，实际多计 100 元。修复：同步时按当前有效状态重新核对，清除 A 留在报表中的旧金额。验证：分别在空报表和已有 A 的报表上同步，均不保留失效金额。”只有已核对真实代码链路后才能采用这个结论，不得照抄案例当作发现。
8. 若工具仅接受缺陷评论，不要通过 Bug、Other、LOW 等标签把待确认项塞进问题列表；使用独立总结或可用的说明渠道记录，并明确说明未确认，不得伪称已输出工具不支持的独立栏目。
